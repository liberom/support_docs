### Complete CircleCI Configuration Example (YAML)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/continuous-integration/circleci.md

A full example `.circleci/config.yml` file demonstrating a workflow with build and deploy jobs. It includes steps for checking out code, restoring/saving bundle cache, building the Jekyll site, running HTML Proofer tests, persisting the build output, installing AWS CLI, and syncing the site to an S3 bucket. Requires the `S3_BUCKET_NAME` environment variable.

```YAML
workflows:
  test-deploy:
    jobs:
      - build
      - deploy:
          requires:
            - build
          filters:
            branches:
              only: master
version: 2.1
jobs:
  build:
    docker:
      - image: cimg/ruby:2.7.4
    environment:
      BUNDLE_PATH: ~/repo/vendor/bundle
    steps:
      - checkout
      - restore_cache:
          keys:
            - rubygems-v1-{% raw %}{{ checksum "Gemfile.lock" }}{% endraw %}
            - rubygems-v1-fallback
      - run:
          name: Bundle Install
          command: bundle check || bundle install
      - save_cache:
          key: rubygems-v1-{% raw %}{{ checksum "Gemfile.lock" }}{% endraw %}
          paths:
            - vendor/bundle
      - run:
          name: Jekyll build
          command: bundle exec jekyll build
      - run:
          name: HTMLProofer tests
          command: |-
            bundle exec htmlproofer ./_site \
              --allow-hash-href \
              --check-favicon  \
              --check-html \
              --disable-external
      - persist_to_workspace:
          root: ./
          paths:
            - _site
  deploy:
    docker:
      - image: cimg/python:3.9.1
    environment:
      S3_BUCKET_NAME: <<YOUR BUCKET NAME HERE>>
    steps:
      - attach_workspace:
          at: ./
      - run:
          name: Install AWS CLI
          command: pip install awscli --upgrade --user
      - run:
          name: Upload to s3
          command: ~/.local/bin/aws s3 sync ./_site s3://$S3_BUCKET_NAME/ --delete --acl public-read
```

### Full Travis CI Configuration File (.travis.yml)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/continuous-integration/travis-ci.md

This is a complete example of a `.travis.yml` file for configuring Travis CI builds for a Jekyll project. It specifies the Ruby language environment, RVM version, a script to run before the main build, the main build script, branch filtering, additional apt packages, bundler caching, and notification settings.

```yaml
language: ruby
rvm:
  - 2.6.3

before_script:
 - chmod +x ./script/cibuild # or do this locally and commit

# Assume bundler is being used, therefore
# the `install` step will run `bundle install` by default.
script: ./script/cibuild

# branch whitelist, only for GitHub Pages
branches:
  only:
  - gh-pages     # test the gh-pages branch
  - /pages-(.*)/ # test every branch which starts with "pages-"

addons:
  apt:
    packages:
    - libcurl4-openssl-dev

cache: bundler # caching bundler gem packages will speed up build

# Optional: disable email notifications about the outcome of your builds
notifications:
  email: false
```

### Git Post-Receive Hook for Jekyll Deployment (Bash)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/deployment/automated.md

A Bash script intended for a Git post-receive hook. It clones the pushed repository, installs Ruby gems using Bundler, builds the Jekyll site, and cleans up the temporary clone. Requires Jekyll and Bundler installed on the server.

```bash
#!/bin/bash -l

# Install Ruby Gems to ~/gems
export GEM_HOME=$HOME/gems
export PATH=$GEM_HOME/bin:$PATH

TMP_GIT_CLONE=$HOME/tmp/myrepo
GEMFILE=$TMP_GIT_CLONE/Gemfile
PUBLIC_WWW=/var/www/myrepo

git clone $GIT_DIR $TMP_GIT_CLONE
BUNDLE_GEMFILE=$GEMFILE bundle install
BUNDLE_GEMFILE=$GEMFILE bundle exec jekyll build -s $TMP_GIT_CLONE -d $PUBLIC_WWW
rm -Rf $TMP_GIT_CLONE
exit
```

### Generating RSS Feed with Liquid

Source: https://github.com/jekyll/jekyll/blob/master/docs/_tutorials/convert-site-to-jekyll.md

This Liquid template generates an RSS 2.0 feed XML file for a Jekyll site. It iterates through site posts, including title, link, description (truncated and escaped), publication date, and a unique GUID based on the post URL. Requires site configuration for title, url, and description.

```liquid
---
layout: null
---

<?xml version="1.0" encoding="UTF-8" ?>
<rss version="2.0" xmlns:atom="http://www.w3.org/2005/Atom">

    <channel>
        <title>{{ site.title }}</title>
        <link>{{ site.url }}</link>
        <atom:link href="{{ page.url | prepend: site.url }}" rel="self" type="application/rss+xml" />
        <description>{{ site.description }}</description>
        <lastBuildDate>{{ site.time | date_to_rfc822 }}</lastBuildDate>
        {% for post in site.posts %}
        <item>
            <title>{{ post.title }}</title>
            <link>
                {{ post.url | prepend: site.url }}
            </link>
            <description>
                {{ post.content | escape | truncate: '400' }}
            </description>
            <pubDate>{{ post.date | date_to_rfc822 }}</pubDate>
            <guid>
                {{ post.url | prepend: site.url }}
            </guid>
        </item>
        {% endfor %}
    </channel>
</rss>
```

### Custom Jekyll Converter for PDF using Kramdown

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/upgrading/3-to-4.md

This Ruby code defines a Jekyll plugin that subclasses `Jekyll::Converter` to enable conversion of `.markdown` files to PDF using the `kramdown-converter-pdf` gem. It requires the `kramdown-converter-pdf` gem to be installed.

```Ruby
module Jekyll
  External.require_with_graceful_fail "kramdown-converter-pdf"

  class Markdown2PDF < Converter
    safe true
    priority :low

    def matches(ext)
      # match only files that have an extension exactly ".markdown"
      ext =~ /^\.markdown$/
    end

    def convert(content)
      Kramdown::Document.new(content).to_pdf
    end

    def output_ext
      ".pdf"
    end
  end
end
```

### Caching Markdown Conversion with Jekyll Cache (Ruby)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_tutorials/cache-api.md

This Ruby snippet demonstrates how to utilize the Jekyll Cache API's `getset` method to cache the result of an expensive function, such as converting Markdown to HTML. It defines a helper method `cache` to get or create a cache instance named "ConvertMarkdown" and a `convert_markdown_to_html` method that uses `cache.getset(markdown)` to ensure `expensive_conversion_method` is only called once for each unique `markdown` input, returning the cached result on subsequent calls.

```ruby
def cache
  @@cache ||= Jekyll::Cache.new("ConvertMarkdown")
end

def convert_markdown_to_html(markdown)
  cache.getset(markdown) do
    expensive_conversion_method(markdown)
  end
end
```

### Defining Custom Jekyll Command with init_with_program (Ruby)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/plugins/commands.md

This code defines a new Jekyll command named :new by subclassing Jekyll::Command. The init_with_program class method is implemented to register the command with the main Jekyll program using the Mercenary library. It sets the command's syntax, description, defines an option (-d or --dest), and specifies the action to be performed when the command is executed, which is creating a new Jekyll site.

```ruby
class MyNewCommand < Jekyll::Command
  class << self
    def init_with_program(prog)
      prog.command(:new) do |c|
        c.syntax "new [options]"
        c.description 'Create a new Jekyll site.'

        c.option 'dest', '-d DEST', 'Where the site should go.'

        c.action do |args, options|
          Jekyll::Site.new_site_at(options['dest'])
        end
      end
    end
  end
end
```

### Implementing a Custom Jekyll Converter in Ruby

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/plugins/converters.md

This Ruby code defines a custom Jekyll converter named `UpcaseConverter`. It demonstrates how to implement the `matches` method to identify files with the `.upcase` extension, the `output_ext` method to specify the output extension as `.html`, and the `convert` method to transform the content by converting it to uppercase. It also sets `safe` to true and `priority` to low.

```Ruby
module Jekyll
  class UpcaseConverter < Converter
    safe true
    priority :low

    def matches(ext)
      ext =~ /^\.upcase$/i
    end

    def output_ext(ext)
      ".html"
    end

    def convert(content)
      content.upcase
    end
  end
end
```

### Generating Category Pages (Ruby)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/plugins/generators.md

This complex generator creates a new page for each category found in the site. The `CategoryPageGenerator` iterates through `site.categories` and appends new `CategoryPage` instances to `site.pages`. The `CategoryPage` class, inheriting from `Jekyll::Page`, defines the structure and data for each generated category page, including setting the filename to 'index.html', the directory to the category name, and initializing data with linked posts and front matter defaults.

```ruby
module SamplePlugin
  class CategoryPageGenerator < Jekyll::Generator
    safe true

    def generate(site)
      site.categories.each do |category, posts|
        site.pages << CategoryPage.new(site, category, posts)
      end
    end
  end

  # Subclass of `Jekyll::Page` with custom method definitions.
  class CategoryPage < Jekyll::Page
    def initialize(site, category, posts)
      @site = site             # the current site instance.
      @base = site.source      # path to the source directory.
      @dir  = category         # the directory the page will reside in.

      # All pages have the same filename, so define attributes straight away.
      @basename = 'index'      # filename without the extension.
      @ext      = '.html'      # the extension.
      @name     = 'index.html' # basically @basename + @ext.

      # Initialize data hash with a key pointing to all posts under current category.
      # This allows accessing the list in a template via `page.linked_docs`.
      @data = {
        'linked_docs' => posts
      }

      # Look up front matter defaults scoped to type `categories`, if given key
      # doesn't exist in the `data` hash.
      data.default_proc = proc do |_, key|
        site.frontmatter_defaults.find(relative_path, :categories, key)
      end
    end

    # Placeholders that are used in constructing page URL.
    def url_placeholders
      {
        :path       => @dir,
        :category   => @dir,
        :basename   => basename,
        :output_ext => output_ext,
      }
    end
  end
end
```

### Handling Page 1 Edge Case and Numbered Pagination - Jekyll Liquid

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/pagination.md

This Liquid snippet provides more robust pagination links, specifically addressing the page 1 edge case where Jekyll doesn't create a '/page1' folder. It generates numbered links for all pages, linking page 1 correctly and using `site.paginate_path` for other pages, while also including 'Prev' and 'Next' links.

```Liquid
{% if paginator.total_pages > 1 %}
<div class="pagination">
  {% if paginator.previous_page %}
    <a href="{{ paginator.previous_page_path | relative_url }}">&laquo; Prev</a>
  {% else %}
    <span>&laquo; Prev</span>
  {% endif %}

  {% for page in (1..paginator.total_pages) %}
    {% if page == paginator.page %}
      <em>{{ page }}</em>
    {% elsif page == 1 %}
      <a href="{{ site.paginate_path | relative_url | replace: 'page:num/', '' }}">{{ page }}</a>
    {% else %}
      <a href="{{ site.paginate_path | relative_url | replace: ':num', page }}">{{ page }}</a>
    {% endif %}
  {% endfor %}

  {% if paginator.next_page %}
    <a href="{{ paginator.next_page_path | relative_url }}">Next &raquo;</a>
  {% else %}
    <span>Next &raquo;</span>
  {% endif %}
</div>
{% endif %}
```

### Create a Custom Jekyll Markdown Processor (Ruby)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/configuration/markdown.md

This Ruby code defines a custom Markdown processor class within the `Jekyll::Converters::Markdown` namespace. It includes an initializer to handle dependencies (like `funky_markdown`) and a `convert` method that takes content and returns the processed HTML.

```ruby
class Jekyll::Converters::Markdown::MyCustomProcessor
  def initialize(config)
    require 'funky_markdown'
    @config = config
  rescue LoadError
    STDERR.puts 'You are missing a library required for Markdown. Please run:'
    STDERR.puts '  $ [sudo] gem install funky_markdown'
    raise FatalException.new("Missing dependency: funky_markdown")
  end

  def convert(content)
    ::FunkyMarkdown.new(content).convert
  end
end
```

### Creating a Custom Jekyll Liquid Tag (Ruby)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/plugins/tags.md

```Ruby
module Jekyll
  class RenderTimeTag < Liquid::Tag

    def initialize(tag_name, text, tokens)
      super

    end

    def render(context)

    end
  end
end

```

### Registering and Triggering Hooks for Custom Jekyll Objects in Ruby

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/plugins/hooks.md

This Ruby code defines a custom Jekyll::Excerpt subclass, HookedExcerpt, which triggers :post_init and :post_render hooks during its lifecycle. It also shows how to register handlers for these custom hooks using Jekyll::Hooks.register, allowing plugins to react to events within instances of this custom class.

```ruby
module Foobar
  class HookedExcerpt < Jekyll::Excerpt
    def initialize(doc)
      super
      trigger_hooks(:post_init)
    end

    def output
      @output ||= trigger_hooks(:post_render, renderer.run)
    end

    def renderer
      @renderer ||= Jekyll::Renderer.new(
        doc.site, self, site.site_payload
      )
    end

    def trigger_hooks(hook_name, *args)
      Jekyll::Hooks.trigger :excerpts, hook_name, self, *args
    end
  end
end

Jekyll::Hooks.register :excerpts, :post_init do |excerpt|
  Jekyll.logger.debug "Initialized:",
                      "Hooked Excerpt for #{excerpt.doc.inspect}"
end

Jekyll::Hooks.register :excerpts, :post_render do |excerpt, output|
  return output unless excerpt.doc.type == :posts
  Foobar.transform(output)
end
```

### Injecting Data into Template Variables (Ruby)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_docs/plugins/generators.md

This Jekyll generator subclass, `Reading::Generator`, demonstrates how to inject computed data into an existing page's data hash. It finds the page named 'reading.html', filters book data based on status ('ongoing', 'finished'), and assigns the results to the page's `data` attributes 'ongoing' and 'done'. This data becomes available as template variables within the 'reading.html' layout.

```ruby
module Reading
  class Generator < Jekyll::Generator
    def generate(site)
      book_data = site.data['books']
      ongoing = book_data.select { |book| book['status'] == 'ongoing' }
      done = book_data.select { |book| book['status'] == 'finished' }

      # get template
      reading = site.pages.find { |page| page.name == 'reading.html'}

      # inject data into template
      reading.data['ongoing'] = ongoing
      reading.data['done'] = done
    end
  end
end
```

### Jekyll Post Date Regex (Original Imprecise)

The initial regular expression used by Jekyll to parse post filenames. It matches three groups of digits separated by hyphens, followed by the title and extension, but does not enforce a specific number of digits for the date parts, allowing invalid dates.

```ruby

```

### Jekyll Post Date Regex (v3.4.0 Strict)

Source: https://github.com/jekyll/jekyll/blob/master/docs/_posts/2017-03-02-jekyll-3-4-1-released.markdown

The updated regular expression introduced in Jekyll v3.4.0 to strictly enforce the YYYY-MM-DD format as per documentation. It requires exactly four digits for the year and two digits for the month and day, inadvertently breaking compatibility with single-digit dates.

```ruby

```
